# Воркфлоу разработки фичи

Единый процесс для агента и пользователя: от идеи до готовой фичи. Правила стека и кода — в `backend/AGENTS.md` и `frontend/AGENTS.md`, здесь только порядок работы.

Артефакты фичи `<name>` (snake_case, имя юзкейса):

| Артефакт | Путь | Назначение |
|----------|------|------------|
| Юзкейс | `docs/usecases/<name>.md` | Что и зачем, предложение по реализации (структура — `docs/usecases/README.md`). Один файл — одна фича, живёт долго |
| План | `.plan/<YYYYMMDD-HHMM>_<name>.md` | Этапы, решения, статус выполнения; один план — одна задача (новая фича или доработка) |

**Имя плана.** Префикс — текущие дата и время создания плана (`date +%Y%m%d-%H%M`), например `.plan/20261010-0410_auth.md`. Так планы не дублируются и сортируются по времени, а доработка уже сделанной фичи получает новый план с тем же `<name>`. Префикс после создания не меняется.
| Диаграммы | `docs/deployment.md`, `*/docs/architecture/` | Источник истины для состава системы, модели данных, маршрутов |

## Принципы

- Порядок фиксированный: юзкейс → план → диаграммы → backend → клиент API → frontend → финал. Этап не начинается, пока не закрыт предыдущий.
- Каждый **стоп** — агент прекращает работу и ждёт явного ответа пользователя. «Двигайся дальше» тоже ответ; молчание — нет.
- План обновляется по ходу работы (не в конце): статус этапа меняется сразу, решения и отклонения записываются в «Принятые решения».
- **План — единственная память между сессиями.** Работа может идти в разных сессиях (чтобы экономить токены), поэтому агент не полагается на контекст диалога: каждый шаг отмечается в плане сразу после выполнения (`[x]`), а не пачкой в конце; перед стопом и перед завершением сессии план должен быть актуален. См. «Работа в нескольких сессиях».
- Расхождение документации и кода не решается молча: сообщить и предложить, что менять.
- Фича касается только backend или только frontend — соответствующие этапы пропускаются с пометкой `[-]` и причиной.
- Коммиты и push — только по просьбе пользователя (см. `CLAUDE.md`).

## Этапы

### 0. Подготовка
- Прочитать `CLAUDE.md`, `AGENTS.md` затронутых частей, `docs/usecases/`, `.plan/` (нет ли уже такой или пересекающейся фичи), релевантные диаграммы.
- Если в `.plan/` есть незавершённый план по этой задаче (есть `[ ]` или `[~]`) — продолжить его (см. «Работа в нескольких сессиях»), а не создавать новый.
- Если фича уточняет или расширяет существующую — **не создавать новый юзкейс**: открыть `docs/usecases/<name>.md` и править его. Новый файл юзкейса — только для новой фичи.

### 1. Юзкейс — стоп
- Если требования неполные, задать вопросы пользователю (только то, что нельзя решить разумным умолчанием; умолчание назвать явно).
- Новая фича: написать `docs/usecases/<name>.md`; уточнение существующей: внести изменения в её файл (в плане указать, какие разделы изменены). Шаблон из `docs/usecases/README.md`: цель, сценарий, backend (сущности, эндпоинты, ошибки, правила), frontend (страницы, состояния, формы), вне рамок. Для нетривиальных потоков — диаграмма последовательности.
- Показать пользователю, внести правки. **Стоп: юзкейс принят.**

### 2. План — стоп
- Создать `.plan/<YYYYMMDD-HHMM>_<name>.md` по шаблону ниже (дату и время взять командой `date +%Y%m%d-%H%M`, не выдумывать): принятые решения, этапы, чекбоксы с конкретными файлами и командами.
- Корнер-кейсы и открытые вопросы вынести в этап «Уточнение» отдельными пунктами.
- **Стоп: план принят.**

### 3. Диаграммы — стоп
- Обновить до кода всё, что меняется: `backend/docs/architecture/data_model.md` и `architecture.md`, `frontend/docs/architecture/routes.md` и `architecture.md`, `docs/deployment.md`.
- Если диаграммы не меняются — записать в плане «изменений нет, подтверждено».
- **Стоп: диаграммы приняты.**

### 4. Уточнение — стоп (по необходимости)
- Пройти корнер-кейсы и вопросы из плана с пользователем, зафиксировать решения в плане.
- **Стоп: решения зафиксированы.** Если вопросов нет — этап пропускается.

### 5. Backend
Порядок по `backend/AGENTS.md`: модель SQLAlchemy → DTO → DAO (интерфейс, реализация, UnitOfWork) → сервис → исключения и маппинг в HTTP → роутер → DI → миграция → env в `.example.env`.
- Тесты пишутся вместе с эндпоинтом, по файлу на эндпоинт.
- Миграция генерируется после правки моделей; применённые не правятся; накатывать без просьбы не нужно.
- Выход из этапа: ruff, mypy и pytest backend зелёные (через `docker compose`). **Стоп: контракт API и backend приняты** — пользователь может проверить Swagger (`/docs`) до начала frontend.

### 6. Клиент API
- Перегенерировать клиент (`pnpm gen:api`); сгенерированные файлы руками не править.
- Проверить, что типы совпадают с юзкейсом; расхождения — к backend, не обход на фронте.

### 7. Frontend
Порядок по `frontend/AGENTS.md`: хуки данных → формы → страницы и маршруты → тесты (vitest; e2e Playwright для ключевого сценария).
- Все состояния экрана из юзкейса: загрузка, пусто, ошибка, успех.
- Выход из этапа: biome, tsc и vitest зелёные. **Стоп: UI принят** (пользователь смотрит на `http://localhost:5173`).

### 8. Финал
- Диаграммы и юзкейс соответствуют результату; расхождения исправлены.
- Все проверки затронутых частей пройдены повторно.
- Итоговый отчёт: что сделано, что запускалось и с каким результатом (включая падения и пропуски), что осталось (допущения, долги).
- В плане все этапы `[x]` или `[-]` с причиной. Коммит — только по просьбе.

## Работа в нескольких сессиях

Цель — запускать каждый этап (или несколько) в свежей сессии с чистым контекстом.

**Старт сессии.** Прочитать `CLAUDE.md`, найти в `.plan/` нужный план (по просьбе пользователя или единственный незавершённый), прочитать его целиком и юзкейс из шапки. Затем читать только то, что нужно текущему этапу (`AGENTS.md` нужной части, диаграммы, файлы из «Журнала»). Продолжить с первого `[~]` или `[ ]`. Если шаг помечен `[~]` — сначала по `git status`/`git diff` проверить, что уже сделано, и не повторять сделанное.

**Во время работы.**
- Шаг выполнен → сразу `[x]`; начат, но не закончен → `[~]` с пометкой, что осталось.
- Принятое решение, отклонение от юзкейса, нетривиальная находка (например, обходной путь в окружении) → в «Принятые решения» или «Заметки» в тот же момент.
- Проверки (ruff, mypy, pytest и т.д.) → в «Журнал» с результатом, включая падения.

**Конец сессии** (стоп, завершение этапа или нехватка контекста). Обновить в плане «Следующий шаг»: одно-два предложения, с чего начать, какие файлы открыть, что осталось нерешённым. Сообщить пользователю, что можно продолжить в новой сессии, и назвать файл плана.

## Шаблон `.plan/<YYYYMMDD-HHMM>_<name>.md`

```markdown
# План: <name>

Юзкейс: [`../docs/usecases/<name>.md`](../docs/usecases/<name>.md). Правила: `backend/AGENTS.md`, `frontend/AGENTS.md`.
Задача: <одна строка: новая фича или что именно дорабатываем>.
Статусы: `[ ]` не начат, `[~]` в работе, `[x]` готов, `[-]` не делаем (с причиной). На «стоп» агент ждёт ответа пользователя.
Агент отмечает шаги сразу после выполнения: план — память между сессиями (`docs/workflow.md`, «Работа в нескольких сессиях»).
```
