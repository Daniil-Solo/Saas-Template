# AGENTS.md

## О проекте

Это frontend-шаблон для быстрого старта приложений (в том числе microSaaS). Репозиторий содержит общий рабочий код, который нужен почти любому веб-клиенту: роутинг, аутентификацию, типизированный API-клиент, серверное состояние, UI-кит, формы, обработку ошибок, тесты. Клиент работает в паре с backend-шаблоном из `../backend`.

Предметная логика конкретного продукта добавляется поверх шаблона: новые страницы и фичи создаются по флоу из раздела «Флоу реализации» ниже. Существующий общий код (auth, shared) расширяй, а не переписывай, если пользователь явно не попросил об обратном.

Описание конкретного продукта (если оно есть) лежит в `../docs/usecases/` (общие для backend и frontend). Перед реализацией новой фичи проверь, нет ли там описания.


## Технологический стек

- Фреймворк и сборка: react, vite, typescript (strict)
- Роутинг: react-router
- Серверное состояние: @tanstack/react-query
- API-клиент: @hey-api/openapi-ts (генерация типов и функций из OpenAPI backend)
- Формы и валидация: react-hook-form, zod
- UI и стили: tailwindcss, shadcn/ui (radix-ui), lucide-react (иконки)
- Клиентское состояние (только если нужно): zustand
- Линтер и форматтер: biome
- Тесты: vitest, @testing-library/react, msw (моки API), playwright (E2E)
- Пакетный менеджер: pnpm


## Структура проекта

Дерево ниже описывает ключевые директории. Актуальное содержимое смотри в файловой системе, а не полагайся на этот список как на исчерпывающий.

- docs/ - документация
  - architecture/ - mermaid-диаграммы проекта
    - architecture.md - контекст клиента, слои, поток данных
    - routes.md - страницы, маршруты и права доступа
  - development.md - запуск проекта, dev-окружение (Docker), линтер, генерация клиента, тесты
- src/ - весь исходный код проекта
  - app/ - сборка приложения
    - providers.tsx - QueryClientProvider и прочие провайдеры
    - router.tsx - объявление маршрутов, guard-ы доступа
    - main.tsx - точка входа
    - styles.css - tailwind и глобальные стили
  - pages/ - страницы-маршруты (одна папка на страницу, только сборка из features и shared)
  - features/ - пользовательские сценарии (формы, действия, связанные хуки)
    - auth/ - вход, регистрация, выход, хранение токена, `useCurrentUser`
  - shared/ - код без привязки к предметной области
    - api/ - HTTP-клиент, обработка ошибок
      - generated/ - сгенерированный клиент (не править руками)
    - ui/ - базовые компоненты (shadcn/ui)
    - lib/ - утилиты и общие хуки
    - config/ - конфигурация из `import.meta.env`
- tests/ - тесты (структура зеркалит `src/`)
  - e2e/ - Playwright-тесты пользовательских сценариев
  - mocks/ - msw-хендлеры и фабрики тестовых данных
  - setup.ts - настройка vitest
- public/ - статические файлы

## Документация - источник истины

Диаграммы в `docs/architecture/` (`architecture.md`, `routes.md`) и общая для проектов схема развертывания `../docs/deployment.md` - источник истины и отправная точка разработки. Код следует за диаграммами, а не наоборот.

- Перед реализацией фичи прочитай релевантные диаграммы и описание в `../docs/usecases/`
- Если фича меняет набор страниц, навигацию или права доступа, состав слоев либо способ развертывания, сначала обнови диаграмму, а затем реализуй код
- Если код и диаграмма расходятся, не подгоняй молча ни одно под другое: сообщи пользователю о расхождении и предложи, что менять
- В конце задачи убедись, что диаграммы соответствуют результату
- Источник истины по контракту API - backend: типы запросов и ответов берутся только из сгенерированного клиента, а не описываются вручную

## Архитектурные слои

Проект использует слоистую архитектуру. Зависимости направлены только вниз:

1. **app** - сборка приложения: провайдеры, роутер. Бизнес-логики нет.
2. **pages** - страницы-маршруты. Компонуют features и shared, не содержат запросов к API напрямую.
3. **features** - пользовательские сценарии. Здесь живут формы, `useQuery`/`useMutation`-хуки и логика взаимодействия с API.
4. **shared** - переиспользуемый код без знания о предметной области (UI-кит, HTTP-клиент, утилиты).

Правила зависимостей:
- Слой импортирует только слои ниже себя; `shared` не импортирует ничего из `features`, `pages`, `app`
- Features не импортируют друг друга напрямую; общий код выноси в `shared`
- Импорты через алиас `@/` (корень - `src/`), без длинных относительных путей `../../..`
- Запросы к API делаются только через сгенерированный клиент из `shared/api`, использование `fetch`/`axios` в компонентах запрещено
- Ошибки API превращаются в понятные пользователю сообщения в одном месте (`shared/api`), а не в каждом компоненте

## Дополнительные сведения

- `docs/development.md` - всё про локальную разработку: запуск проекта, dev-окружение (Docker), установка зависимостей, линтер, генерация клиента, тесты
- Серверное состояние живет в TanStack Query; не дублируй данные с сервера в zustand/useState
- Токен доступа хранится в одном модуле `features/auth`; остальной код получает его только через API-клиент
- Тексты интерфейса - на русском языке

## Важно

- Отвечай всегда на русском языке
- Все команды проекта (pnpm, biome, tsc, vitest, playwright) выполняются внутри docker-контейнера, команды описаны в `docs/development.md`. На хосте зависимости не ставятся
- Для добавления библиотек используй `pnpm add ...` (внутри контейнера) вместо ручной правки package.json, чтобы lock-файл оставался согласованным
- TypeScript строгий: не используй `any`, `@ts-ignore` и `as`-приведения ради «заглушить» ошибку; тип неизвестной структуры проверяй через zod или type guard
- Не правь файлы в `src/shared/api/generated/` вручную: меняется контракт - перегенерируй клиент (`pnpm gen:api`)
- Если нужного эндпоинта нет в backend, не придумывай его на клиенте: сообщи пользователю, что нужно доработать backend
- Компоненты - функциональные, один компонент на файл, имена файлов компонентов в kebab-case (`login-form.tsx`), компоненты и типы - PascalCase
- Новые UI-компоненты shadcn добавляй командой `pnpm dlx shadcn@latest add <компонент>`, а не копируй код вручную
- Стили - только Tailwind-классы; произвольный CSS допустим лишь в `styles.css`. Не используй inline `style` без необходимости
- Любой экран с данными обрабатывает четыре состояния: загрузка, пусто, ошибка, успех
- Формы: схема zod + react-hook-form, ошибки валидации показываются рядом с полем; кнопка отправки блокируется на время запроса
- Доступность: интерактивные элементы - семантические теги (`button`, `a`), у полей есть `label`, у иконок-кнопок - `aria-label`
- Не храни секреты и ключи в коде и в репозитории; всё из `VITE_*` попадает в бандл и публично. Новые переменные окружения добавляй в `src/shared/config/` и в `.example.env`
- Не используй `dangerouslySetInnerHTML` без санитизации и не логируй токены/персональные данные
- Не удаляй docker-тома (`down -v`) без явной просьбы пользователя

## Флоу реализации страницы или фичи

Порядок: обновить диаграмму маршрутов `docs/architecture/routes.md` → убедиться, что эндпоинты есть в backend, и перегенерировать клиент → хуки данных в feature → компоненты feature → страница → маршрут → тесты.

### Обновление API-клиента

Если backend получил или изменил эндпоинт, перегенерируй клиент (команда `pnpm gen:api`, см. `docs/development.md`). Сгенерированные типы (например, `UserDTO`) и функции используются как есть.

### Хуки данных (feature)

Запросы оборачиваются в хуки в `src/features/<feature>/api.ts`. Ключи запросов - массивы, начинающиеся с имени сущности.

```ts
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

import { createEntity, listEntities } from "@/shared/api/generated";
import type { EntityCreateDTO } from "@/shared/api/generated";

export const entitiesKey = ["entities"] as const;

export function useEntities() {
  return useQuery({
    queryKey: entitiesKey,
    queryFn: async () => (await listEntities({ throwOnError: true })).data,
  });
}

export function useCreateEntity() {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: async (body: EntityCreateDTO) =>
      (await createEntity({ body, throwOnError: true })).data,
    onSuccess: () => queryClient.invalidateQueries({ queryKey: entitiesKey }),
  });
}
```

### Форма (feature)

Схема zod описывает поля и сообщения валидации; сабмит вызывает мутацию.

```tsx
const schema = z.object({
  title: z.string().min(1, "Введите название"),
});
type FormValues = z.infer<typeof schema>;

export function EntityForm() {
  const { mutate, isPending, error } = useCreateEntity();
  const form = useForm<FormValues>({ resolver: zodResolver(schema) });

  return (
    <form onSubmit={form.handleSubmit((values) => mutate(values))}>
      <Label htmlFor="title">Название</Label>
      <Input id="title" {...form.register("title")} />
      <FieldError message={form.formState.errors.title?.message} />
      {error ? <FormError error={error} /> : null}
      <Button type="submit" disabled={isPending}>Создать</Button>
    </form>
  );
}
```

### Страница и маршрут

Страница в `src/pages/entities/entities-page.tsx` только компонует features и обрабатывает состояния экрана. Маршрут добавляется в `src/app/router.tsx` с указанием доступа (публичный / приватный) в соответствии с `docs/architecture/routes.md`.

### Тесты

- Компонент и хук: `tests/` зеркалит `src/`, запросы мокаются через msw (`tests/mocks/`), без обращений к реальному backend
- Проверяй поведение глазами пользователя (`getByRole`, `getByLabelText`), а не детали реализации
- Критичные пользовательские сценарии (вход, основной флоу фичи) покрываются E2E в `tests/e2e/`
